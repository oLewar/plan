# AGENTS.md — LLM Wiki Schema for `pro/plan`

## Mission
Исследуем мир, чтобы выявлять причинно-следственные связи между событиями, и проектируем эффективные способы решения возникающих проблем.

Ключевая метрика: **эффективность** (ценность результата / затраты времени и риска).

## Three-layer architecture

1. **Raw inbox** (`raw/`) — входящая свалка новых материалов (без подпапок), автоматически маршрутизируемая во внешние тематические разделы.
2. **Wiki** (`wiki/`) — межсвязная база знаний в markdown, поддерживаемая агентом.
3. **Schema/process** (`AGENTS.md`, `processes/`) — правила, по которым агент ведёт wiki.

## Non-negotiable rules

- `raw/` — только inbox: без подпапок, без ручной долгой сортировки; материалы должны быть вынесены во внешние разделы ingest-процессом.
- Любое исследование фиксируется в `wiki/` с ссылками на источники.
- Новые инсайты из диалога/ответов сохраняются как страницы wiki, а не теряются в чате.
- Безопасность обязательна: перед рискованными действиями фиксировать ограничения и проверки.
- Каждое изменение wiki отражать в `wiki/index.md` и `wiki/log.md`.

## Vault structure (Obsidian-first)

- `00_System/` — системная навигация и MOC-хабы.
- `10_Reference/` — справочная информация и стандарты.
- `20_Personal/` — персональные установки, миссия, стиль.
- `25_Projects/` — проектные справочники (по папке на проект).
- `30_Tasks/` — `Backlog`, `In-Progress`, `Done`.
- `40_Research/` — ресерч-поток и синтез.
- `50_Hypotheses/` — проверка гипотез и эксперименты.
- `60_Archive/` — неактуальные и superseded материалы.
- `raw/` — входящая свалка (только корень, без вложенных папок).
- `wiki/` — curated knowledge graph (index/log/concepts/sources/analyses/questions).

## Wiki structure

- `wiki/index.md` — контентный каталог всех страниц.
- `wiki/log.md` — хронологический append-only журнал операций.
- `wiki/overview.md` — текущая картина домена и активные гипотезы.
- `wiki/entities/` — сущности (люди, компании, системы, инструменты).
- `wiki/concepts/` — концепты, механики, причинные паттерны.
- `wiki/sources/` — конспекты конкретных источников.
- `wiki/analyses/` — синтезы, сравнения, выводы, предлагаемые решения.
- `wiki/questions/` — открытые вопросы и пробелы данных.
- `wiki/lint-reports/` — отчёты health-check.

## Standard operation modes

### 1) INGEST (one source)

When a new source appears in `raw/`:

1. Создать/обновить страницу в `wiki/sources/`.
2. Обновить связанные страницы `entities/`, `concepts/`, `analyses/`.
3. Добавить/обновить внутренние ссылки между страницами.
4. Зафиксировать противоречия с ранее известными данными.
5. Добавить запись в `wiki/log.md`.
6. Обновить `wiki/index.md`.

### 2) QUERY (answer + compounding)

When answering questions:

1. Читать `wiki/index.md` как точку входа.
2. Извлекать релевантные страницы и собирать ответ с цитированием.
3. Если ответ дал устойчивый инсайт — сохранить как новую/обновлённую страницу в `wiki/analyses/`.
4. Отразить изменение в `wiki/log.md` и `wiki/index.md`.

### 3) LINT (periodic health-check)

Проверять:

- противоречия между страницами,
- устаревшие утверждения,
- сиротские страницы без ссылок,
- важные концепты без отдельных страниц,
- пробелы в данных и приоритеты доисследования.

Результат писать в `wiki/lint-reports/YYYY-MM-DD.md` + запись в `wiki/log.md`.

## Linking and citation conventions

- Использовать wiki-ссылки формата `[[path/to/page]]`.
- Утверждения с фактами сопровождать блоком `Sources:` со ссылками на `wiki/sources/...`.
- Для гипотез явно помечать статус: `Hypothesis`, `Confirmed`, `Refuted`, `Unknown`.

## Efficiency rubric (for decisions)

При выборе следующего шага приоритизировать максимальный:

1. **Impact** — влияние на цель исследования.
2. **Confidence gain** — насколько шаг уменьшит неопределённость в причинно-следственной модели.
3. **Cost** — время/сложность/риск.
4. **Safety** — отсутствие/контроль побочных рисков.

Формула приоритета (эвристика):
`Priority = (Impact × Confidence gain × Safety) / Cost`

## QMD requirement (mandatory)

- Для навигации и поиска по базе использовать `qmd` как стандартный поисковый слой.
- Минимум: поддерживать коллекции `plan-wiki` и `plan-raw` в актуальном состоянии.
- После значимых изменений markdown запускать `qmd update`.
- Периодически запускать `qmd embed` для актуализации semantic/hybrid поиска.
- Перед сложным синтезом использовать `qmd query ...` и фиксировать результаты обратно в `wiki/`.

См. детальный регламент: `processes/qmd.md`.

## Git workflow

- Ветка по умолчанию: `main`.
- Коммиты атомарные и осмысленные (`feat(wiki): ...`, `docs(process): ...`).
- После каждого ingest/query/lint: обновить индекс, лог, затем коммит.
- Для query/lint задач считать обязательным шагом проверку через `qmd`.
